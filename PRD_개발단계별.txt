====================================================================
 지오펜싱 기반 순차 여행 미션 추천 앱 - PRD (개발 단계별)
 작성일: 2026-08-27
 버전: v1.0 (데모 기획 단계)
====================================================================

[문서 성격]
본 PRD는 "데모를 먼저 만들어 팀원에게 설명하고, 이를 바탕으로 정식
기획안을 작성"하는 것을 목표로 한다. 단, 데모라고 해서 기술적으로
확장 불가능한 지름길을 택하지 않는다. 모든 핵심 기능은 최종본까지
이어질 수 있는 "기초 기술"로 구현하고, 데모 단계에서는 범위(지역,
예산, 로그인 여부)만 축소한다.


====================================================================
1단계. 개요 및 목표
====================================================================

1-1. 한 줄 정의
사용자가 지도 위에 무작위로 "다트"를 던져 여행지 대분류를 정하고,
AI가 사용자 취향과 이동 이력에 기반해 한 번에 1~2곳씩만 다음 여행지를
순차적으로 추천 --> 사용자가 도착해 사진으로 미션을 인증하면 다음
장소가 열리는, 게이미피케이션 기반 즉흥 여행 추천 서비스.

1-2. 문제 정의
- 여행 계획 자체가 피로한 사람들을 위해 "계획을 대신 짜주되, 한 번에
  다 보여주지 않아 매 순간 서프라이즈를 유지"하는 경험을 제공한다.
- 기존 여행 앱(트리플, 대한민국 구석구석 등)은 전체 일정을 한 번에
  보여주는 방식이라 "선택 피로"와 "스포일러"가 발생한다.

1-3. 데모의 목표
- 팀원에게 핵심 플로우(다트 던지기 -> 지역 추천 -> 미션 추천 -> 사진
  인증 -> 다음 미션)가 실제로 동작함을 보여준다.
- 이 데모를 근거로 정식 기획안(팀 배분, 일정, 예산)을 작성한다.

1-4. 최종본의 목표 (참고용, 이번 데모 범위 아님)
- 네이티브 앱(iOS/Android) 전환
- 로그인/계정 기반 취향 데이터 누적 및 개인화 고도화
- 숙소 추천 및 예약 대리(수익 모델)
- 전국 단위 커버리지


====================================================================
2단계. 범위 정의 (데모 vs 최종본)
====================================================================

  항목               | 데모 (이번 산출물)      | 최종본 (향후)
  -------------------|--------------------------|---------------------------
  플랫폼             | 웹(PWA)                  | 네이티브 앱(iOS/Android)
  지역 범위          | 서울 서부                | 전국
                      | (마포·서대문·은평·강서)  |
  로그인             | 없음 (완전 익명)         | 선택적 로그인, 취향 DB 누적
  숙소               | 사용자 직접 입력만(A)    | 추천 + 예약 대리(B, 수익모델)
  LLM                | OpenRouter (무료/저가 모델) | Claude API
  지도/장소 데이터   | Kakao Map/Local API      | Kakao + 대체/보강 소스 검토
                      | 무료 사용량 한도 내      | 주당 $40 예산 내 유료 사용
  DB                 | 없음 (localStorage만)    | 서버 DB(사용자, 이력, 취향)
  스킵/대체 추천     | 포함                     | 포함
  사진 위치 인증     | EXIF GPS 우선 시도       | 동일 + 서버 검증 강화
  SNS 연동           | 없음(자체 편집·정리만)   | 없음(동일 방침 유지)

데모에서 "없음"으로 표시된 항목도 아키텍처 상 나중에 이어붙일 수
있도록 설계한다 (예: localStorage 스키마를 DB 스키마와 최대한 유사하게
설계 -> 3단계 참고).


====================================================================
3단계. 핵심 사용자 플로우
====================================================================

[0] 취향 설문 (온보딩)
    - 로그인 여부와 무관하게 매 "여행 시작" 시점마다 노출
    - 질문: 여행 템포(느긋/보통/빡빡), 선호 테마(자연/맛집/카페·감성/
      액티비티/역사문화 - 복수선택), 동행 형태(혼자/커플/친구/가족),
      예산대(저가/중가/고가)
    - 이 응답은 세션 동안만 사용, DB 저장 없음(데모 기준)

[1] 숙소 입력 (선택)
    - "숙소가 정해져 있나요?" -> 있으면 주소 텍스트 입력 또는 지도에서
      핀 찍기 -> 좌표 저장(세션 상태)
    - 없으면 건너뛰기 가능 (숙소 없이도 전체 플로우 진행 가능)

[2] 다트 던지기 (지역 대분류 선정)
    - 화면 전체 지도(서울 서부 범위)에 애니메이션으로 다트가 랜덤 좌표에
      꽂힘
    - 다트 좌표를 중심으로 반경 내 주변 행정동/지역들을 POI 밀도 x
      거리 가중치로 정렬 -> 최소 1개, 최대 3개 지역 카드 제시
      (예: 다트가 대성리 인근에 꽂히면 "대성리 / 가평 / 청평" 목록)
    - 사용자는 가중치 슬라이더(거리 민감도)를 조절해 재정렬 가능
    - 사용자가 지역 카드 중 하나 선택

[3] 첫 여행지 추천
    - 선택된 지역 + 취향 설문 응답 + (있다면) 숙소 좌표를 종합해
      1~2곳의 구체적 방문지(관광지/카페/맛집 등) 추천
    - 각 추천 카드에 AI가 생성한 추천 이유 텍스트 포함
    - 사용자가 하나 선택 -> "미션 시작"

[4] 미션 인증 (도착 확인)
    - 사용자가 실제 장소에 도착 -> 앱 내 카메라로 즉석 촬영(갤러리
      업로드 불가)
    - 사진 EXIF GPS 메타데이터 추출 시도 -> 미션 목적지 좌표와의
      거리가 임계값 이내면 자동 인증
    - EXIF 좌표를 못 읽는 경우(iOS 브라우저 제약 등) -> 브라우저
      Geolocation API로 촬영 시점 위치를 별도 캡처해 대체 검증
    - 인증 완료 시 사진 + 장소명 + 시간을 미션 이력에 저장(세션 내)

[4-1] 스킵 (장소 방문 불가 시)
    - 미션 카드에 "여기 갈 수 없어요" 버튼
    - 선택 시 동일 지역 내 대체 후보 1곳을 즉시 재추천

[5] 다음 여행지 추천 (반복)
    - 방금 완료한 미션 위치(현재 위치) + 지금까지의 미션 이력(방문한
      곳들의 카테고리/테마) + (있다면) 향후 들를 숙소 좌표를 함께
      고려해 다음 1~2곳 추천
    - [3]~[5] 과정을 사용자가 "여행 종료"를 누를 때까지 무한 반복

[6] 기록 정리 및 공유용 편집
    - 여행 종료 시 그동안 쌓인 미션 사진들을 타임라인/그리드 형태로
      자동 정리
    - 사진 위에 방문 장소명, 순서, 날짜 등을 오버레이하는 간단 편집
      기능 제공(SNS 직접 연동은 하지 않음, 이미지 저장/다운로드까지만)


====================================================================
4단계. 기능 요구사항 상세
====================================================================

4-1. 다트 던지기 & 지역 추천 로직
  - 입력: 서울 서부 경계 폴리곤(또는 bounding box)
  - 처리:
    1) bounding box 내 무작위 좌표 1개 생성 (다트 좌표)
    2) 다트 좌표 기준 반경 R(예: 5~10km, 조정 가능한 상수) 내에서
       Kakao Local API 카테고리 검색(관광명소/카페/음식점/문화시설)으로
       하위 지역 후보들의 POI 개수 집계 -> 밀도 점수화
    3) 각 후보 지역에 대해 점수 = POI밀도 x (1 + 사용자설정값 x
       거리가중치함수(다트와의 거리))
       * 사용자설정값: UI 슬라이더로 0~1 등 범위 조정, 기본값은 팀 협의
       * 거리가중치함수는 가까울수록 값이 커지는 감쇠 함수(역수 또는
         지수감쇠) 사용 - 정확한 함수 형태는 5단계 개발 중 튜닝 필요
    4) 점수 상위 최대 3개 지역을 카드로 제시 (POI가 희박한 지역이면
       1~2개만 제시될 수 있음)
  - 역지오코딩: Kakao의 좌표->행정동 변환 API로 다트 좌표 및 후보
    좌표들의 지역명(읍/면/동)을 사람이 읽을 수 있는 이름으로 변환

4-2. 다음 여행지 추천 로직 (LLM 연동)
  - 입력: 현재 위치 좌표, 선택된 대분류 지역, 취향 설문 응답, 미션
    이력(장소명+카테고리 리스트), 숙소 좌표(있는 경우)
  - 처리:
    1) Kakao Local API로 현재 위치 반경 내 후보 장소 목록(카테고리별)
       조회
    2) (숙소가 있는 경우) 숙소 방향으로도 편향되도록 후보군에 숙소
       인근 장소를 일부 포함
    3) 후보 목록 + 취향/이력 정보를 프롬프트로 구성해 OpenRouter
       경유 LLM에 전달 -> 1~2곳 선정 + 각 추천 이유 생성
    4) 이미 방문한 장소는 후보에서 제외
  - 출력: 추천 장소 카드(이름, 카테고리, 좌표, 추천 이유, 예상 이동
    거리/시간)

4-3. 사진 미션 인증
  - 카메라 촬영만 허용(파일 업로드 비활성화 - PWA의 capture 속성 또는
    MediaDevices API 활용)
  - 1차: EXIF GPS 파싱 -> 목적지 좌표와의 거리 계산 -> 임계값(예:
    200m, 팀 협의 필요) 이내면 자동 통과
  - 2차 폴백: EXIF 파싱 실패 또는 위치 정보 없음 -> 촬영 직후
    브라우저 Geolocation API로 별도 위치를 요청해 같은 방식으로 검증
  - 두 방법 모두 실패(권한 거부 등) 시 수동 확인 모드(사용자가 "여기
    맞음"을 직접 체크) - 데모 한정 임시 허용, 최종본에서는 재검토

4-4. 취향 설문
  - 폼 형태, DB 저장 없이 세션 상태(React state 또는 localStorage)에만
    유지
  - 항목: 템포(단일선택), 테마(다중선택), 동행 형태(단일선택), 예산대
    (단일선택)

4-6. 여행 범위 단위 선택
  - 지역 후보를 어느 행정 단위로 묶을지 사용자가 고른다
    - 광역자치단체(시·도) / 기초자치단체(시·군·구) / 읍면동
    - 기본값은 기초자치단체 - 읍면동은 하루 여행 범위로 너무 좁고
      광역은 한 번의 추천 루프로 감당하기에 너무 넓다
  - 단위를 바꾸면 표본 추출 반경과 POI 집계 반경이 함께 바뀐다
    (좁은 단위에 넓은 반경을 쓰면 엉뚱한 지역까지 후보로 올라오고,
     넓은 단위에 좁은 반경을 쓰면 표본이 바다·산에 떨어진 지역의
     POI 수가 비정상적으로 낮게 잡혀 순위가 뒤집힌다)
  - 단위 변경은 지역 후보를 다시 받아야 한다(거리 가중치 슬라이더와
    달리 클라이언트 재정렬로 해결되지 않음)

4-7. 현재 위치 기준 거리 안내 (데모 미구현, 실기기 단계에서 적용)
  - 목적: 다트/직접 선택으로 정해진 여행지가 지금 내 위치에서 얼마나
    떨어져 있는지 보여줘 "갈지 말지"를 판단할 수 있게 한다
  - 표시 위치: 지역 후보 카드와 확정된 여행지 화면
  - 값: 현재 위치 ↔ 지역 대표 좌표의 직선 거리(haversine).
    경로 탐색은 하지 않으며 실제 이동 거리와 다를 수 있음을 문구로 밝힌다
  - 선행 조건: 브라우저 Geolocation 권한. 권한을 받는 시점은
    "여행 시작" 직후가 아니라 지역 후보를 처음 보여줄 때로 한다
    (권한 요청을 처음 화면에 붙이면 이탈률이 오른다)
  - 권한 거부/실패 시: 거리 항목만 숨기고 나머지 플로우는 그대로 진행한다.
    거리 표시는 부가 정보이므로 실패가 여행을 막아서는 안 된다
  - 데모에서 빠지는 이유: HTTPS 와 실기기 권한 동의가 필요하고,
    데스크톱 브라우저의 IP 기반 위치는 오차가 수 km라 값이 의미를 잃는다

4-5. 로컬 데이터 저장 (익명 사용자)
  - localStorage에 다음을 세션 단위로 저장:
    - 현재 여행 세션 ID(임시, 새로고침 시 유지용)
    - 취향 설문 응답
    - 숙소 좌표(입력한 경우)
    - 지금까지의 미션 이력(장소, 좌표, 시간, 사진 - 사진은 브라우저
      메모리/IndexedDB, localStorage는 용량 한계로 메타데이터만)
  - 브라우저를 닫거나 다른 기기로 접속하면 이력 초기화(데모 정책)


====================================================================
5단계. 데이터 모델 (향후 DB 이관을 고려한 설계)
====================================================================

데모는 DB가 없지만, localStorage/IndexedDB 스키마를 아래 구조에 맞춰
설계하면 최종본에서 서버 DB로 그대로 이관하기 쉽다.

TripSession (여행 세션)
  - session_id
  - created_at
  - preferences { tempo, themes[], companion, budget }
  - accommodation { lat, lng, address } | null
  - dart_point { lat, lng }
  - selected_region { name, lat, lng }
  - status (진행중/종료)

Mission (미션 = 방문 장소 1건)
  - mission_id
  - session_id (FK)
  - place_name
  - lat, lng
  - category
  - recommend_reason (LLM 생성 텍스트)
  - order_index (몇 번째 미션인지)
  - status (추천됨/진행중/완료/스킵됨)
  - photo (완료 시)
  - verified_by (exif | geolocation | manual)
  - completed_at

※ 최종본에서는 여기에 User(사용자), UserPreferenceHistory(누적 취향),
  Accommodation(예약 대리 시 예약 상태) 등이 추가된다.

6단계. 기술 스택 및 아키텍처 (데모 기준)
====================================================================

- 프레임워크: Next.js (React 기반, PWA 설정으로 카메라/위치 권한
  접근 - 웹이지만 앱과 유사한 UX 제공)
- 백엔드: Next.js API Routes (별도 서버 없이 프론트와 한 프로젝트로
  운용 - 가벼운 스택 요구사항 충족)
- 데이터 저장: 브라우저 localStorage + IndexedDB(사진 등 대용량),
  서버 DB 없음
- 지도/장소: Kakao Map JavaScript SDK(지도 렌더링) + Kakao Local
  REST API(장소 검색, 역지오코딩) - 무료 사용량 한도 내 운용
- LLM: OpenRouter API (무료 또는 저가 모델 사용, 데모 예산 절약)
- 사진/위치: 브라우저 MediaDevices/Camera capture API, exif-js 등
  EXIF 파싱 라이브러리, Geolocation API

※ 최종본 전환 시: Next.js -> React Native/Flutter 네이티브 앱,
  Next.js API Routes -> 별도 백엔드 + DB, OpenRouter -> Claude API로
  교체를 전제로 설계(비즈니스 로직과 API 클라이언트를 분리해 두면
  전환 비용이 낮아짐)
